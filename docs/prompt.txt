── 지금 Dispatcher가 어떻게 동작하나 ─────────────────────────────────

브로커에는 Dispatcher라는 개념이 있어. Dispatcher 하나는 특정 소비자(consumer)에게 메시지를
보내는 송신 단위야. 각 Dispatcher는
  - 자기 식별자인 consumerId,
  - 메시지를 보낼 대상인 host,
  - 어떤 토픽을 받을지 정하는 pattern (예: order.*)
을 가져. "1 consumerId = 1 Dispatcher" 규칙이 있어.

지금은 이 Dispatcher들을 JSON 파일 하나(dispatchers.json)로만 관리해. 브로커가 시작할 때
이 파일을 읽어서 각 항목을 Dispatcher로 등록하는 방식이야(파일 → 빈 등록). 그리고 등록된
Dispatcher들을 담아두고, 들어온 메시지를 매칭되는 Dispatcher로 넘겨주는 DispatcherContainer가
있어.

── 문제 ──────────────────────────────────────────────────────────

지금 구조에선 Dispatcher를 바꾸려면 파일을 고치고 브로커를 재시작해야 해. 운영 중에 소비자를
새로 붙이거나, 대상 주소·구독 패턴을 바꾸거나, 없애려면 매번 재기동이 필요한 거지. 이게 불편해.

── 필요한 기능 ───────────────────────────────────────────────────

애플리케이션이 실행되는 중에 HTTP API로 Dispatcher를 추가·수정·삭제할 수 있게 하고 싶어.
단, 지금의 파일 기반 관리는 그대로 유지하면서, 런타임 변경이 파일에도 반영돼서 재기동해도
유지되게 해줘.

구체적으로:
  - 추가: consumerId·host·pattern을 전부 요청 본문으로 받아 새 Dispatcher를 등록.
  - 수정: 기존 Dispatcher의 id를 기준으로 새 정보를 받아 바꿔. 바꿀 수 있는 건 host와 pattern
    두 가지야. consumerId는 식별자라 수정 대상이 아니고, id는 경로 변수로, 본문엔 새 host·pattern만
    담으면 돼.
  - 삭제: id를 경로 변수로 받아 해당 Dispatcher를 제거.

입력 형식:
  - host는 https://example.com:8080 같은 URL 문자열로 받아서 내부 Host 객체로 파싱해야 해.
  - pattern은 문자열로 받아 내부 패턴 타입으로 변환.

── 네가 설계에서 고민해줬으면 하는 것들 ───────────────────────────

  - 런타임 변경을 파일과 어떻게 동기화할지. 재기동 후에도 변경이 남아야 하고, 도중에 프로세스가
    죽어도 설정 파일이 깨지면 안 돼.
  - DispatcherContainer는 메시지 처리 핫패스에서 계속 읽히는 공유 객체야. 런타임에 이걸 안전하게
    바꾸려면 동시성을 어떻게 다룰지.
  - "수정"이 이미 실행 중인 Dispatcher에게 무슨 의미인지 — 주소나 패턴이 바뀌면 기존 구독·전송
    상태(이미 처리 중이거나 밀린 메시지)를 어떻게 이어갈지.
  - 잘못된 입력, 없는 id, 중복 id 같은 상황을 적절한 HTTP 상태 코드로 응답.
  - 이 전부를 테스트로 검증.
